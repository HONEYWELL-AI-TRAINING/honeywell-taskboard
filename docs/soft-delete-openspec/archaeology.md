## 2. Existing design patterns

| Pattern in use | Where | Do I have to follow it? |
|----------------|-------|-------------------------|
| Repository owns database reads/writes; service owns validation and missing-task behavior. | `backend-dotnet/src/TaskBoard.Api/Repositories/TaskRepository.cs`; `backend-java/src/main/java/com/honeywell/taskboard/repository/TaskRepository.java`; `backend-python/repositories/task_repository.py`; corresponding task services | Yes. | Missing tasks become `TaskNotFound`/`TaskNotFoundException`, mapped to HTTP 404; successful DELETE returns 204. | `backend-python/routers/tasks.py:74`; `backend-dotnet/src/TaskBoard.Api/Controllers/TasksController.cs:75`; `backend-java/src/main/java/com/honeywell/taskboard/web/TaskController.java:75` | Yes, unless the approved API contract changes. |
| Task queries are in repositories; status filtering is supported for list and count where implemented. | .NET `ListAsync`/`GetAsync`; Java custom `findByOptionalStatus` and inherited `JpaRepository` methods; Python `list`/`count`/`get` | Yes. Deleted rows must be excluded consistently from every relevant read method, including inherited Java query surfaces if they remain available. |
| Database schema is managed centrally, not by runtime ORM migrations. | `database/schema.sql`; `TaskBoardContext.cs`; Java `TaskItem.java`; Python `models/task.py` | Yes. A soft-delete marker needs a schema change and matching entity/model mappings in each backend. |

## 5. Coding conventions

- Naming: Python uses `snake_case`; .NET uses PascalCase methods with `Async` suffix; Java uses camelCase.
- File/module layout: each backend separates HTTP/controller, service, repository, and model/entity concerns; shared schema is in `database/schema.sql`.
- Test naming & structure: Python uses pytest functions; .NET uses xUnit facts; Java uses JUnit 5 with Mockito/AssertJ. API tests cover HTTP status codes; service tests cover service/repository interactions.
- Anything the linter/formatter enforces: no repository-wide formatter/linter requirement was established during this trace.

## 6. Archaeology summary (the part you carry forward)

- The 3–5 files that are the true centre of this change:
  - `database/schema.sql`
  - `backend-python/repositories/task_repository.py`
  - `backend-dotnet/src/TaskBoard.Api/Repositories/TaskRepository.cs`
  - `backend-java/src/main/java/com/honeywell/taskboard/repository/TaskRepository.java`
  - Corresponding task models and service/API tests must also be updated.
- The pattern the change must follow: add the soft-delete state to the shared schema and all three model mappings; perform the state change in each repository/service stack; hide deleted tasks in every applicable read path; preserve the existing 204/404 API contract unless the approved spec says otherwise.
- The existing behaviour the change modifies (state it precisely): DELETE currently removes the task row; subsequent normal reads cannot find it. The intended change is to retain the row but make it invisible to ordinary reads.
- Tests that will need updating vs tests that must not move: Python `test_delete_task` and `test_delete_then_get_raises` currently assert hidden-as-404 and can continue passing under soft delete. .NET `DeleteAsync_RemovesExistingTask` and Java `deleteRemovesExistingTask` pin repository-delete calls and need revision for the new implementation. Keep the 204 controller tests unless the API response contract changes.
- Task comments and cascade: no `task_comments` table, model, FK, cascade implementation, or comment tests are present in the current code/schema. The comments feature brief says deleting a task should take its comments with it; the soft-delete brief says comments must survive soft delete and restore. This is a documented future dependency, not a cascade currently implemented by this repository.
- Query methods to audit for deleted-row exclusion:
  - .NET: `TaskRepository.ListAsync` (status-filterable), `TaskRepository.GetAsync`; no count method.
  - Java: `TaskRepository.findByOptionalStatus`; inherited `JpaRepository` reads including `findAll`, `findAllById`, `findById`, `existsById`, and `count`.
  - Python: `TaskRepository.list` (status-filterable), `TaskRepository.get`, and `TaskRepository.count` (status-filterable). Its fake equivalents are in `backend-python/tests/conftest.py`.
